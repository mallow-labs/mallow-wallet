# Development Workflow & CLI

Common tasks and commands. Build and contribution requirements live in
[CONTRIBUTING.md](../CONTRIBUTING.md); this page is the day-to-day reference.

## Build commands

```bash
flutter pub get
./di.sh          # code generation (freezed, retrofit, injectable, swagger)
flutter test
./run.sh         # run on the default device with .env compiled in
```

🛑 **Always run `./di.sh`, never `dart run build_runner build` at the repository
root.** The root's generated mocks reference types from the packages under
`packages/`, so those must build first. Build the root first and mockito
silently falls back to `dynamic`, producing a wall of `invalid_override` errors
that look like your fault and are not. `di.sh` builds the leaf packages in
parallel, clears their build cache, and only then builds the root.

No generated file is checked in, so codegen is a required step on a fresh
clone, not an optimisation.

## Adding a new feature

1. Create a directory in `lib/features/<feature>/`.
2. Define models (`models/`), repository (`data/`), and bloc (`services/`).
3. Build UI in `screens/` and `widgets/`.
4. Register dependencies with `@injectable`, then re-run `./di.sh`.
5. Register the route in `lib/core/router/app_router.dart` — add the path to
   `AppRoutes` and the `GoRoute` to the router built by `createRouter`.

See [architecture.md](architecture.md) for the conventions each layer follows,
including the `Result<T, AppFailure>` error-handling pattern blocs use.

## Testing requirements

1. **Cryptographic operations** — derivation, signing, key parsing — must be
   covered exhaustively. These are the paths where a bug is unrecoverable.
2. **Blocs** — test the state transitions, and prefer `bloc_test`.
3. **Repositories** — mock the API client. The suite uses **mockito** with
   `@GenerateMocks` (regenerated by `./di.sh`) in most places, and `mocktail`
   where a mock is declared inline.
4. **Security flows** — cover the biometric gates and secure-storage access,
   and assert the fail-closed branches rather than only the happy path.

Tests need no configuration: nothing reads config from disk at runtime. To vary
a `Config` value in a test, use the `Config.debugOverrides` map (`--dart-define`
is const, so it cannot be changed per test) and clear it in `tearDown`.

## End-to-end tests

`test/e2e/` holds a fully offline harness — a headless Android emulator driven
against a local mock backend, no network and no credentials. See
[test/e2e/README.md](../test/e2e/README.md).
